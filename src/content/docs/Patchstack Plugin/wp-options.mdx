This reference describes WordPress plugin **2.3.8**, including the options it registers and additional state it creates while running. Defaults below are the values used when an option is first added; an upgrade preserves values that already exist. Patchstack App policies and license synchronization can supply different values.

Most hardening features require a connected paid site. An option being stored does not make a feature available on a free site. For the user-facing controls, see [Hardening](/patchstack-app/site-dashboard/hardening/app-hardening-general/).

<Aside type="caution">
The option names in the reference tables omit the `patchstack_` prefix. Use the full name, such as `patchstack_login_2fa`, in WordPress or WP-CLI. Boolean settings use `1` for on and `0` for off; WordPress may return stored scalar values as strings.
</Aside>

## Storage and multisite

Most settings, credentials and log tables belong to an individual site. Use `wp --url=https://site.example option update ...` to select a subsite.

On multisite, `.htaccess` rule selection and the legacy `auto_update` selection are read as **network options**. A network administrator can change these through the network settings or [`wp site option update`](https://developer.wordpress.org/cli/commands/site/option/update/). The remote-management grant below is also network-scoped. A per-site policy or signing key does not grant authority to change shared software.

2FA enrollment and throttling belong to the shared WordPress user account and are stored in user metadata, not in the site's options table. See [login protection](/patchstack-app/site-dashboard/hardening/app-hardening-login-protection/).

## Additional runtime and network state

These entries are created as needed, rather than registered with the configuration defaults above. They are not additional App policy settings.

| Full option name | Scope | Purpose |
| --- | --- | --- |
| `patchstack_network_plugin_updates` | Network; defaults to off | Network administrator's grant for remote management using the primary site's signing key. Despite its name, it covers more than plugin updates. See [multisite permissions](/patchstack-plugin/installing-patchstack-on-a-multisite/#remote-management-and-plugin-updates). |
| `patchstack_vulnerable_plugins` | Network, or single-site | Pending legacy vulnerable-only plugin updates. Failed attempts remain pending for retry. |
| `patchstack_2fa_enforced` | Network | Expiring internal lookup of whether a network has a site enforcing 2FA. |
| `patchstack_db_version` | Site | Database schema version string, separate from the plugin version. |
| `patchstack_log_schema_lock`, `patchstack_log_schema_attempts`, `patchstack_log_schema_retry_after` | Site | Migration lease, retry count and next retry time. Use the database-update controls instead of editing these. |
| `patchstack_firewall_log_processing`, `patchstack_eventlog_processing` | Site | Expiring upload leases containing an expiry and owner token; these are no longer boolean switches. |
| `patchstack_firewall_log_ap_processing` | Site; obsolete | Legacy auto-prepend processing flag, removed during import. |
| `patchstack_htaccess_rules_hash`, `patchstack_htaccess_removal_pending` | Network, or single-site | Last managed-rule fingerprint and pending hardening removal. |
| `patchstack_cron_offset` | Site | Stored offsets for scheduled jobs. |

Other internal keys include retry queues, signature-replay records and transient counters. They are not supported configuration switches. 2FA user metadata uses the `patchstack_2fa_` prefix; existing `webarx_2fa_` enrollment is read as a fallback and migrated when it can be saved completely. Let the plugin handle this migration.

## Logging and login protection

`block_bruteforce_ips` controls the IP-based login ban. It works independently of `activity_log_is_enabled`, `activity_log_failed_logins` and `activity_log_failed_logins_db`. Turning activity logging off does not disable login-ban counters or an active ban.

In the current plugin, failed-login audit events follow the main activity logger. `activity_log_failed_logins` remains registered for settings compatibility; it is not a separate enforcement switch. `activity_log_failed_logins_db` controls whether failed-login audit events are included in uploads to Patchstack App.

The 2FA account limit is separate again: five invalid codes trigger a five-minute cooldown. The login-ban attempt and duration settings do not change that limit. See [login protection](/patchstack-app/site-dashboard/hardening/app-hardening-login-protection/).

## Existing installations and `.htaccess`

Updating the plugin or refreshing unchanged API rules does not, by itself, rewrite existing hardening blocks to adopt a different installation layout. A change to the hardening rules or relevant settings can trigger a write. An explicit empty rules string from the API removes its hardening rules; a missing or malformed response preserves them. Turning the last hardening option off queues removal and retries it if writing fails.

`disable_htaccess` and `PS_DISABLE_HTACCESS` stop these writes, including removal. They do not delete existing blocks or stop security headers added at runtime. See [.htaccess hardening](/patchstack-app/site-dashboard/hardening/app-hardening-htaccess/).

## Legacy automatic updates

Patchstack App no longer offers a switch to enable automatic updates. Existing `auto_update` selections can still run until disabled. The plugin respects WordPress's global automatic-update policy; vulnerable-only updates retain failed work for retry. See [Packages](/patchstack-app/site-dashboard/site-software/#automatic-updates).

## Minimal mode

To keep the PHP firewall enabled while disabling optional hardening and activity logging, apply the following settings before activation. On an existing installation, they do not remove `.htaccess` rules already written. Review any existing auto-prepend installation separately before changing shared server configuration.

For a single site, use [`wp option update`](https://developer.wordpress.org/cli/commands/option/update/):

```bash
wp option update patchstack_basic_firewall 1
wp option update patchstack_disable_htaccess 1
wp option update patchstack_basicscanblock 0
wp option update patchstack_prevent_default_file_access 0
wp option update patchstack_index_views 0
wp option update patchstack_block_debug_log_access 0
wp option update patchstack_block_fake_bots 0
wp option update patchstack_proxy_comment_posting 0
wp option update patchstack_image_hotlinking 0
wp option update patchstack_pluginedit 0
wp option update patchstack_userenum 0
wp option update patchstack_hidewpversion 0
wp option update patchstack_application_passwords_disabled 0
wp option update patchstack_xmlrpc_is_disabled 0
wp option update patchstack_json_is_disabled 0
wp option update patchstack_add_security_headers 0
wp option update patchstack_disable_curl_decoding 0
wp option update patchstack_mv_wp_login 0
wp option update patchstack_login_2fa 0
wp option update patchstack_block_bruteforce_ips 0
wp option update patchstack_captcha_on_comments 0
wp option update patchstack_captcha_login_form 0
wp option update patchstack_captcha_registration_form 0
wp option update patchstack_captcha_reset_pwd_form 0
wp option update patchstack_activity_log_is_enabled 0
wp option update patchstack_activity_log_failed_logins 0
wp option update patchstack_activity_log_failed_logins_db 0
wp option update patchstack_auto_update '[]' --format=json
```

This also turns off 2FA enforcement, login bans, CAPTCHA and login-URL protection on that site. On multisite, another site's policy can still require 2FA for a shared account. These settings do not change firewall whitelists or virtual patches.

On multisite, run the per-site settings for each intended site using `--url`. To stop network hardening writes and legacy automatic updates as well, a network administrator can use:

```bash
wp site option update patchstack_disable_htaccess 1
wp site option update patchstack_auto_update '[]' --format=json
```
